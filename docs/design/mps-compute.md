# MPS calculation contract

Manage owns the browser-safe pure function `computeMpsWorkflow` in the public `dsh-agent-manage/mps-compute/workflow` module. The package exposes source, JavaScript and declaration paths through `./mps-compute/*`. Workbench normalizes the current evaluation draft, source read status, relation snapshot and same-version shipment result. This module performs no reads, writes or authorization.

The input contains an evaluation context, product dimensions, explicit category demand, monthly sales submissions, last-year shipments, opening inventory, source capacity candidates and local constraints. M+1 equals the evaluation month. M+4 remains at category level. Rows at base, material group and SKU grain exist for M+1 through M+3.

For each month and category, both sources expose material-group/category, nationwide SKU/group and base-SKU/nationwide-SKU quantities and ratios. Their direct base-SKU/category shares are averaged before multiplying by category demand. Zero intermediate denominators remain null in the layer formulas; a complete positive category can still establish a true zero direct share. The product set must cover the source records. A missing quantity, duplicate product key, unmatched source record, failed current read or zero denominator prevents the dependent share and demand. Valid zero quantities remain zero. No piece-rounding rule is assumed; the last positive-weight row receives only the floating-point residual needed to reconcile with category demand.

Category demand uses only the current MPS product-table SKU pool and its categories. Workbench reclassifies recent BI actuals, DMS plans, historical monthly shipments and annual SKU plans through this pool. Out-of-pool or ambiguously classified records remain in a separate completion list and do not block uniquely classified pool records. Nationwide category totals retain valid source quantities without requiring a base; base-level workflow rows still require their base keys. Category demand remains the explicit input seam of the workflow. Each input row carries effective `quantity` and may supply `systemQuantity` separately; an absent baseline uses `quantity` for existing callers, while explicit null preserves an unknown baseline. Inherited effective changes from earlier months continue into demand and inventory without replacing the original system values. Workbench now supplies calculated values through `computeMpsCategoryDemand` from `mps-compute/category-demand`. Opening plans use the three months ending two months before the evaluation month; adjusted plans end one month before it. The base is the final actual month. Each historical year aggregates nationwide category quantities before calculating factors; three complete years are averaged equally. The first two months average the chained month-over-month method and the annual-estimate share method, then divide by aggregate actual/plan attainment. M+3 and M+4 extend the preceding result by adjacent annual-plan month ratios. Missing DMS completeness blocks final correction while independent BI methods remain available. No model prediction substitutes for these inputs. Missing category demand does not remove valid shares, opening inventory or source capacities. Negative projected closing inventory is preserved as opening inventory. A source income field missing from historical shipments does not invalidate valid shipment quantities.

Each material group's fallback SKU is last-year same-month nationwide Top1, with equal quantities ordered by code. Unadjusted inputs retain the direct two-source shares. Accepted final-share edits leave other nonfallback shares unchanged; the fallback absorbs the group residual and distributes it in proportion to its original averaged two-source base-SKU/category shares. Explicitly edited fallback base rows remain fixed while the remaining fallback bases split the residual using their normalized original system shares. If every fallback base is edited, the group must balance exactly. Invalid, duplicate, incomplete-source or negative-residual edits are rejected through `adjustmentIssues`, preserving the group's system shares. Category and final-share edits are optional public inputs. Results retain system and effective values; effective category edits also feed subsequent annual-ratio months. The caller owns edit history, identity and draft persistence.

Safety inventory uses base safety days multiplied by next month's effective demand divided by that next calendar month's days. Zero safety days establishes zero safety inventory even when next demand is unknown; absent safety days remains unknown. The third SKU month uses fourth-month category demand and third-month effective shares only as an inventory reference. No fourth-month SKU row is created. Required production is `max(0, demand + targetInventory - openingInventory)`. Opening inventory accepts signed same-version previous-step quantities and then rolls forward through unconstrained projected closing inventory. `evaluation: 'unconstrained'` applies to all rows, including later months after an overload. `mainPlan` remains null because these calculations do not create an executable schedule.

Capacity requires explicit positive SKU tons-per-piece coefficients, unique base resource IDs, tunnel/forming resource kinds, base-month production days and explicit SKU resource allocation shares summing to one within each kind. Allocation candidates and daily ton/piece ratios never establish a weight or an allocation. Legacy capacity candidates remain separate display facts, and SKU monthly capacity, load and gap fields remain null. Resource loads use allocated required tons divided by daily tons and production days. Loads below 90% are normal, 90% through 105% are warning, and above 105% are overload. Resource-level excess days and ton gaps use the same allocations. Explicit zero capacity/days leaves load undefined while preserving computable ton gaps; production days cannot exceed calendar days. Missing either resource kind, invalid allocation or weight prevents a complete evaluation. Shared resources appear once per month. Unknown allocations also keep unassigned candidate resources unknown.

Each row and resource returns nullable quantities and missing reasons. The summary separates the strict total, known ton subtotal and evaluated scope; incomplete scope does not imply full feasibility. Local inputs do not represent formal saving or an active scheduling rule. Transfer, outsourcing, merged-base mappings and executable scheduling still require explicit business decisions.

`tests/mps-workflow.test.mjs` exercises the public pure function with worked inputs, zero values, missing data, source coverage and reconciliation. `pnpm test:mps-compute` runs these checks. The normal TypeScript build emits the JavaScript and declaration files; Workbench's author build resolves the public source export and bundles it for the browser.
