# 分仓补货确认与去 DMS 下单解释 — 规则与阈值

## 1. 角色分工（铁律）

```text
看板：实际补货量维护 → 保存草稿 → 形成提交备份 → 打开 DMS 并预填（通过接口写入）
DMS ：客户/产品/库存/车型/交期校验 → 正式订单创建 → 提交 → 返回 DMS 单号
OMS ：定时回收 Agent 来源订单 → 核对订单号、数量与状态
Agent（右侧问答）：解释规则 → 查询与表述状态 → 边界顶回；不写入、不执行
```

| 事项 | Agent（对话侧） | 看板 | DMS | OMS |
|---|---|---|---|---|
| 建议补货量 | 解释与展示 | 展示 | 不负责 | 不负责 |
| 实际补货量维护 | **不执行** | 负责 | 不负责 | 不负责 |
| 草稿保存 | **不执行** | 负责 | 不负责 | 不负责 |
| 提交备份形成 | **不执行** | 负责 | 不负责 | 不负责 |
| DMS 预填上下文生成与打开 | **不执行** | 负责 | 接收并校验 | 不负责 |
| 客户与收货信息校验 | 不负责 | 不负责 | 负责 | 不负责 |
| 产品、库存、车型、交期校验 | 不负责 | 不负责 | 负责 | 不负责 |
| 订单创建与提交 | 不负责 | 提交动作 | 负责 | 不负责 |
| 订单状态核对 | 只查不推 | 展示 | 保留来源标识与返回单号 | 负责回收核对 |

**Agent 不重做 DMS 的订单创建与校验能力**，也不绕过用户确认直接调用 DMS 下单接口。

## 2. 建议量与实际量的关系与调整规则

| 项目 | 规则 |
|---|---|
| 系统建议补货量 | 固化规则计算结果，只作为判断依据，**不视为已下单** |
| 实际补货量 | 业务在看板确认后的数量 |
| 允许关系 | 实际量可等于、低于或高于建议量 |
| 低于建议量 | **必须填写原因** |
| 高于建议量 | 必须说明订单、活动、节令或其他依据 |
| 保存与提交 | 保存下单量 ≠ 提交下单；提交后以专业系统返回状态为准 |
| 保存方式 | 建议量与实际量分开保存，实际量**不覆盖**建议量 |
| 明确为 0 | 不进入 DMS 订单明细 |
| 未修改的建议 SKU | 可进入 DMS，不要求用户逐行加入 |

建议量与实际量不一致时的差异原因归纳方向（每条须标注证据状态，最多 5 条）：

| 方向 | 典型差异原因 | 证据状态 |
|---|---|---|
| 人工判断 | 客户实际接货节奏、活动或节令备货、到货时间安排 | 有支撑未验证 |
| 人工判断 | 实际量低于建议量且填写了明确原因 | 已验证（有原因记录时） |
| 数据口径 | 人工调整时点与建议量生成时点不同，库存或订单已变化 | 有支撑未验证 |
| 参数变更 | 补货周期或计划版本发生变化导致建议量重算 | 已验证（有变更记录时） |
| 供给约束 | 基地可供不足或调拨安排限制导致下调 | 有支撑未验证 |
| 数据缺失 | 调拨中或目标库存缺失，建议量本身口径不完整 | 数据缺失 |

## 3. 状态口径（六档，必须准确区分）

| 业务实际状态 | 允许表述 | 禁止表述 |
|---|---|---|
| 已在看板维护并保存实际量 | 「本次确认已保存，尚未提交」 | 「已下单」 |
| 已形成下单前预览并打开 DMS 预填 | 「已生成下单前预览并在 DMS 完成预填」 | 「已提交 DMS」 |
| 已形成提交备份 | 「本次提交内容已形成备份」 | 「订单已创建」 |
| DMS 已返回单号或暂存成功 | 「DMS 已返回单号，正式订单状态以 OMS 回收结果为准」 | 「已发货」「已完成」 |
| 提交失败或超时 | 「提交未成功，业务确认值与备份仍保留，请核对后重试」 | 「提交成功」 |
| 仅保存未提交 | 「已保存下单量」 | 「已提交下单」 |

Agent 在对话侧只能**读取并转述**上述状态，不能改变状态，也不能因为用户查看或追问而推断状态已推进。

## 4. 草稿与提交备份的读口径

| 对象 | 业务含义 | Agent 可做 / 不可做 |
|---|---|---|
| 补货确认草稿 | 看板保存的本次确认结果，只含用户修改结果 | 可查询并转述是否已保存、覆盖范围；不可保存、不可修改、不可清空 |
| 提交备份 | 点击去 DMS 时记录的本次完整提交量快照，用于识别实际提交量与支持单号回写 | 可查询并转述是否已形成、对应范围与时间；不可创建、不可覆盖 |
| 覆盖规则 | 无 DMS 单号的二次提交可覆盖原备份；已关联 DMS 单号的记录不得覆盖，必须形成新记录 | 可解释规则；不执行覆盖判断 |
| 草稿清空 | DMS 暂存或提交成功并返回 DMS 单号后由看板清空当前草稿 | 可解释时机；不执行清空 |
| 单号回写 | DMS 单号回写到对应提交记录 | 可查询回写状态；不执行回写 |

## 5. 提交前核对清单（解释时逐项对照）

有权限业务人员提交前应核对：

1. 当前缺货量与缺货订单
2. 当前可用库存与两类在途（已下单未发货 / 已发货未入库）
3. 91 天及以上大日期、滞库风险与库存批次
4. 基地可用库存、基地在途与未来 7 日排产能否承接
5. 实际补货量与调整原因
6. 目标月份、计划版本与来源（月初 / 滚动、人工 / BI）

## 6. 边界顶回话术

| 用户要求 | 正确回应要点 |
|---|---|
| 「帮我自动下单」 | Agent 不执行下单；说明看板确认与 DMS 提交路径，以及为何需要人工确认 |
| 「直接帮我提交」 | 同上；说明 Agent 权限不等于 DMS 下单权限 |
| 「帮我把实际量改成 300」 | 对话侧不写入；给出看板操作路径与需要填写的原因要求 |
| 「能不能绕过 DMS」 | 不能；DMS 是正式订单创建、校验与提交的唯一系统 |
| 「这就等于下单了吧」 | 明确区分：建议 / 确认 / 草稿 / 预填 / 已提交 / 已下单 |
| 「你在对话里帮我确认就行」 | 说明确认与提交必须在看板由有权限人员完成并留痕 |

顶回时必须给出可执行的替代路径，不能只说"不支持"。

## 7. 对话动作前置约束（预留，当前不启用）

若后续开放对话内动作能力（维护实际量、保存草稿、打开 DMS 预填），必须同时满足以下条件，缺一不可：

1. **意图识别**：把口语确认落到明确的分仓、客户、提货点、SKU 与目标数量。
2. **权限校验**：Agent 访问权限 + DMS 补货订单新增权限 + 客户/地址/产品下单权限 + 账号身份映射，四者齐备。
3. **显式确认**：用户必须对将要提交的完整明细做一次显式确认，未确认不得写入。
4. **防误提交**：说明性追问不得触发写入；不得由 Agent 自行推断数量或自行提交。
5. **留痕同源**：对话动作的留痕必须与看板同源（操作人、时间、原值、新值、原因），不得形成两套记录。
6. **覆盖规则一致**：二次提交覆盖规则与看板一致，已关联 DMS 单号的记录不得覆盖。
7. **降级一致**：不自动处理 DMS 校验失败；不依赖 DMS 实时回传。

在未启用前，对话侧一律按第 1 节与第 6 节处理。

## 8. 失败与异常处理（对话侧解释口径）

| 情况 | 处理 |
|---|---|
| DMS 校验失败 | 由 DMS 处理与提示；Agent 说明以 DMS 校验结果为准，不自动处理 |
| 提交失败或超时 | 说明业务确认值与提交备份仍保留、本次未成功，给可核对项 |
| 权限不足 | 说明缺少哪一类权限（Agent 访问 / DMS 下单 / 客户产品权限 / 身份映射），不暗示可绕过 |
| 打开 DMS 失败或 Token 失效 | 说明需在看板重新发起打开动作以获取新的预填，不复用旧上下文 |
| 预填内容与预览不一致 | 说明以看板预览与实际确认量为准，需重新生成，不在对话侧修正 |
| OMS 尚未回收 | 说明订单状态待回收核对，不推断订单已创建或数量 |
| 数据缺失 | 缺数按 0、不估算；说明无法判断的部分 |

## 9. 数据完整性校验

必备字段：分仓、SKU 与数量、数据截止时间；问差异时还需建议补货量与构成。缺任一必备字段则说明缺失项并只输出可判断部分。

可选字段缺失时：无草稿或备份记录 → 不推断状态；无调整原因 → 说明原因未记录，提示需补录；权限信息缺失 → 不判断能否打开 DMS。

## 10. P2 承接

对话动作能力及其意图识别、权限校验与防误提交机制；待办 / 事件闭环与升级审批；提交失败自动转事件；DMS 正式订单状态自动回传与核对闭环；责任判定与协同角色推荐；修改差异长期分析与合规审计。
