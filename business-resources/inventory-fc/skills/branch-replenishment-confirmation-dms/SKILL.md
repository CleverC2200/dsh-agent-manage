# 分仓补货确认与去 DMS 下单解释 Skill

## 适用范围声明（先读）

本 Agent 的右侧问答**只读、不写库、不执行动作**。实际补货量的维护、草稿保存、提交备份形成、打开 DMS 预填，**全部在看板完成**（看板通过接口写入）。因此本 Skill 在对话侧只承担三件事：

1. **解释**：建议量与实际量为什么不同、调整规则、确认与提交的分界。
2. **查询与表述**：补货确认清单、草稿状态、提交备份、DMS 单号回写状态、提交结果。
3. **边界顶回**：用户要求"自动下单/直接提交/帮我改量"时，说明 Agent 不执行动作，给出正确的操作路径。

对话侧**不**创建、不修改、不覆盖任何业务记录，也不生成 DMS 预填上下文、不打开 DMS。若后续开放对话操作能力，本 Skill 需同步启用 `rules.md` 第 7 节的对话动作前置约束（意图识别、权限校验、显式确认、防误提交），当前不启用。

## 目标

把补货确认这一段作业讲清楚、查清楚：建议补货量与实际补货量的关系、谁能改、改了要留什么、什么算保存什么算提交、去 DMS 之后由谁校验与提交、DMS 单号与提交备份是什么状态；同时明确 Agent 在对话侧不执行任何写入动作。

## 触发场景

- 「实际补货量和建议补货量为什么不一样」「我改了 300 件可以吗」
- 「这份确认保存了吗」「提交了吗」「提交备份是什么」
- 「点了去 DMS 下单是不是就下单了」「DMS 单号回来了吗」
- 「能不能帮我自动下单」「能不能直接改实际量」「能不能绕过 DMS」
- 「提交失败怎么办」「为什么还要在 DMS 再校验一次」

## 输入契约

| 输入项 | 说明 | 必填 |
|---|---|---|
| 确认范围 | 分仓、客户、提货点、目标月份、SKU 范围 | 是 |
| 建议补货量 | 系统建议值及构成（缺货量、库存差额、调拨中） | 是 |
| 实际补货量 | 业务在看板确认的值（等于、低于或高于建议量） | 是（用户问差异时） |
| 调整原因 | 实际量低于或高于建议量时的依据 | 条件必填 |
| 草稿与备份状态 | 草稿是否保存、提交备份是否形成、是否已关联 DMS 单号 | 否 |
| 下单权限 | Agent 访问权限 + DMS 补货订单新增权限 + 客户/地址/产品下单权限 + 账号身份映射 | 否（仅在解释"为什么我打不开 DMS"时取） |
| 数据截止时间 | 建议量对应的库存、订单、在途、目标快照时间 | 是 |

**Agent 权限不能替代 DMS 下单权限**：Agent 允许查看，不代表 DMS 允许下单。

## 执行步骤

### 第 1 步：复核建议补货量与实际补货量
读取建议补货量并展示其构成（缺货量、库存差额、调拨中），再与实际补货量对比，给出差异量与差异方向。**建议量不是已确认量，实际量也不覆盖建议量**，两者分开保存。

### 第 2 步：确认数据时间与版本
确认建议量对应的库存、订单、在途、目标快照时间，以及补货周期值（未配置按默认 7 天并标注）和计划版本与来源。说明结论的时效边界。

### 第 3 步：解释调整规则与差异原因
按 `rules.md` 第 2 节解释：实际量可等于、低于或高于建议量；**低于建议量必须填原因，高于建议量必须说明订单、活动、节令或其他依据**；明确改为 0 的 SKU 不进入 DMS 明细；未修改的建议 SKU 也可进入。差异原因归纳为：人工判断（客户、活动、到货节奏）、数据口径差异、目标或周期变更、基地可供不足等，每条标注证据状态。

### 第 4 步：查询并表述状态
按 `rules.md` 第 3 节与第 4 节取草稿与提交备份状态，按状态表述六档给出准确说法（已保存实际量 / 已形成下单前预览 / 已记录提交备份 / DMS 已返回单号 / 提交未成功 / 仅保存未提交）。**不得把草稿、预览或备份描述为已下单或已提交。**

### 第 5 步：说明后续由谁执行
明确分工：看板负责实际量维护、草稿保存与提交动作；DMS 负责客户、产品、库存、车型、交期校验与正式订单创建提交；Agent 不重做这些校验、不自动处理校验失败。**Agent 不依赖 DMS 实时回传**正式订单状态，订单是否实际创建与数量以 OMS 定时回收结果为准。

### 第 6 步：边界顶回
用户要求自动下单、直接提交、代为改量或绕过 DMS 时，按 `rules.md` 第 6 节说明：Agent 只提供解释与查询，正式动作必须由有权限业务人员在看板与 DMS 完成，并给出正确操作路径与需要确认的点。不承诺到货时间。

### 第 7 步：说明权限前置与失败处理
用户问"为什么打不开 DMS"或"提交失败"时，按 `rules.md` 第 8 节说明四类权限前置，以及提交失败时业务确认值与提交备份仍保留、以专业系统返回状态为准、需核对后重试；事件与升级闭环属 P2，P1 只给可核对项与处理方向。

### 第 8 步：形成交付结果
按 **branch-policy 输出规范** 输出，并在结尾给出白名单内的下一步引导（查看建议量构成、查看缺货明细、查看基地可供、打开工作台完成确认）。

## 规则与阈值

详细规则见 `rules.md`。核心摘要：

- **右侧问答只读**：不保存实际量、不存草稿、不形成提交备份、不生成预填、不打开 DMS
- 系统建议量与实际补货量**分开保存**；实际量不覆盖建议量
- 低于或高于建议量必须记录原因；实际量为 0 的 SKU 不进 DMS 明细
- 状态表述六档不得混用；建议 ≠ 确认 ≠ 草稿 ≠ 预填 ≠ 已提交 ≠ 已下单
- 看板负责确认与提交动作；DMS 负责正式下单与全部校验；Agent 不复制校验逻辑
- Agent 权限不能替代 DMS 下单权限；DMS 必须重新校验
- 不依赖 DMS 实时回传，以 OMS 定时回收为准；不承诺到货时间

## 默认交付

1. 核心结论（建议量与实际量是否一致、差异方向与可能原因）
2. 本次确认范围（分仓、客户、提货点、目标月份、数据时间、补货周期）
3. 建议补货量构成（缺货量、库存差额、调拨中）
4. 建议量与实际量对比（含差异与原因）
5. 状态说明（草稿 / 提交备份 / DMS 单号回写 / 提交结果，按六档准确表述）
6. 执行分工与下一步（谁在看板做什么、DMS 做什么）
7. 权限前置说明（仅在相关时）
8. 数据边界与不可判断项

## 边界与禁止动作

- **不在对话侧执行任何写入**：不保存实际量、不存草稿、不形成提交备份、不生成预填、不打开 DMS
- 不在 Agent 内创建、校验或提交 DMS 正式订单；不自动提交补货订单
- 不复制 DMS 的库存、车型、交期校验逻辑；不自动处理 DMS 校验失败
- 不自动修改客户主数据、收货地址或物流配置
- 不把建议量、草稿、备份或预填描述为已下单或已提交
- 不越权确认：实际补货量必须由有权限业务人员确认
- 不依赖 DMS 实时回传正式订单状态；不承诺到货时间
- P1 不做待办、事件、反馈闭环、定责、升级与责任角色推荐

## P2 承接

对话动作能力（在对话内维护实际量、保存草稿、打开 DMS 预填）及配套的意图识别、权限校验与防误提交机制；待办 / 事件闭环与升级审批；提交失败自动转事件；DMS 正式订单状态自动回传与核对闭环；责任判定与协同角色推荐；修改差异长期分析。
