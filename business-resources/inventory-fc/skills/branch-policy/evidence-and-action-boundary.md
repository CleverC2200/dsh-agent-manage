# 分仓库存证据状态与行动边界规范

定义结论的证据状态标准，以及 AI 可以做什么、不可以做什么。

## 一、证据状态

| 状态 | 含义 | 使用场景 | 输出要求 |
|---|---|---|---|
| 已验证 | 有直接数据支撑 | 系统直接读取的库存、订单、在途、货龄、计划数值 | 直接陈述事实，标注来源与时间 |
| 有支撑未验证 | 有间接数据关联，缺直接验证 | 多指标关联推断，如「订单扣减后可供库存不足叠加在途不足」；推演类结论 | 说明支撑依据，标注待进一步验证 |
| 推测 | 基于经验或模式的合理推测 | 「疑似基地排产推迟」 | 不得作为结论，须给验证建议 |
| 数据缺失 | 因数据不足无法判断 | 计划缺失、在途未接入、客户未覆盖 | 说明缺什么数据及对结论的影响 |

标注方式：在结论后用方括号标注，例如「原因线索：备单中剩余未占用量高于当前可用库存【已验证】」「原因线索：基地在途未按计划入库【推测】」。
推演类结论（未来 7 / 14 日预计超龄）统一按【有支撑未验证】标注，并说明窗口、是否扣减预计消耗、是否排除当前已超龄库存。

## 二、行动边界

### 2.1 AI 可以做的

读取与展示数据；计算指标（缺货量、订单扣减后可供库存、库存差额、建议补货量、调拨中、回顾与展望周转天数、货龄结构、健康库存占比、满足率）；按规则识别风险；输出原因线索（带证据状态）；生成建议（标注待人工确认）；解释口径与计算方法；查询并转述补货确认状态（草稿、提交备份、DMS 单号回写）。**不执行任何写入动作。**

### 2.2 AI 不可以做的

不修改正式计划、目标库存、补货周期配置（除业务在页面确认保存）、库存、订单；不绕过大数据标准结果自行拼接源系统明细；不在 Agent 内创建、校验或提交 DMS 正式订单；不复制 DMS 的库存、车型、交期校验逻辑；不自动提交补货订单；不自动修改客户主数据、收货地址或物流配置；不建、不关、不升级待办与事件；不做正式定责；不承诺到货时间。

### 2.3 本 Agent 不做任何写入

**右侧问答是只读通道，没有任何写入例外。** 以下动作全部由看板通过接口完成，Agent 只在对话侧解释规则、查询状态与顶回越界请求：

| 动作 | 由谁执行 | Agent 在对话侧可做 |
|---|---|---|
| 维护与保存实际补货量 | 看板 | 解释调整规则与差异原因；查询已保存值 |
| 保存补货确认草稿 | 看板 | 查询并转述草稿是否存在、覆盖范围 |
| 形成提交备份 | 看板 | 查询并转述备份是否形成、对应范围与时间 |
| 生成预填上下文并打开 DMS | 看板 | 解释由谁执行、DMS 会重新校验 |

Agent 不得在对话中替代上述任何动作；也不得因为用户查看或追问而推断业务状态已推进。留痕（操作人、时间、原值、新值、原因）由看板侧统一记录，不形成两套记录。

### 2.4 P1 不做、留待 P2 的事项

| 事项 | 说明 |
|---|---|
| 待办 / 事件 / 历史反馈闭环 | P1 只出报告与建议，状态流转未实现 |
| 责任判定与责任角色推荐 | P1 不输出责任人、协同人；事件默认责任角色属业务维护规则包 |
| 升级与审批 | 不做升级判断、不自动创建事项 |
| 30 日大日期超龄推演 | P1 只支持未来 7 日与 14 日窗口 |
| 大日期专项台账与锁定 | P1 只识别 91 天及以上库存并给出处理方向 |
| DMS 正式订单状态回传 | Agent 不依赖 DMS 实时回传，以 OMS 定时回收为准 |

### 2.5 必须人工确认的事项

| 事项 | 说明 |
|---|---|
| 实际补货量 | 由业务确认与调整，Agent 只给建议量 |
| 四个计划 | 人工提报代表业务确认；版本与来源优先级由固化规则执行，业务不能按 SKU 回退 |
| 补货周期 | 业务在页面维护并保存；临时修改只影响预览 |
| 大日期与滞库处理方案 | 是否处理、如何去化由业务与运营确认 |
| 基地资源承接 | 基地能否承接、替代基地与到货安排由业务确认 |
| 口径与数据异常 | 版本冲突、计划不完整、字段缺失、数据过期需人工复核 |

### 2.6 P1 阶段不做清单（八件事，全局禁令；下面是唯一权威枚举，2.1–2.5 为其细则）

1. 不重新生成或覆盖大数据计算的四个正式计划；不用对话中的临时计算替代正式计划。
2. 不绕过大数据标准结果自行拼接源系统（OMS / WMS / SAP）明细。
3. 不在 Agent 内创建、校验或提交 DMS 正式订单；不复制 DMS 的库存、车型、交期校验逻辑。
4. 不自动提交补货订单，不自动修改客户主数据、收货地址与物流配置。
5. 不自动创建、关闭或升级事项与事件，不正式定责。
6. 不擅自改变指标公式、计划版本与来源优先级、补货周期规则或权限规则。
7. 不执行任何写入动作：不保存实际补货量、不保存补货确认草稿、不形成提交备份、不生成 DMS 预填上下文、不打开 DMS——这些全部在看板完成。
8. 不自行制定或编造业务阈值（滞库阈值、紧急补货时限、满足率下限、大日期关注阈值）。

> **右侧问答是只读通道，没有任何写入例外。** 实际补货量维护、补货确认草稿、提交备份、DMS 预填与打开 DMS 全部在看板完成（看板侧统一留痕）；正式订单创建、校验与提交仍由 DMS 完成。对话侧只解释规则、查询状态与顶回越界请求。
>
> **P1 范围外（留待 P2）**：待办与事件闭环、历史反馈闭环、正式定责与责任角色推荐、升级审批、30 日超龄推演、大日期专项台账与锁定。见 2.4 节。

## 三、建议与执行的区分

| 场景 | 正确表述 | 错误表述 |
|---|---|---|
| 补货 | 「建议关注补货节奏（待人工确认）」 | 「已补货 5000 件」 |
| 去 DMS 下单 | 「已生成下单前预览，可在 DMS 确认并提交」 | 「已下单」「已提交 DMS」 |
| 处理建议 | 「建议优先消化 60-90 天库存」 | 「已下达去化指令」 |
| 原因分析 | 「疑似基地排产推迟导致到货延迟」 | 「基地排产推迟导致到货延迟」 |
| 风险判断 | 「存在滞库风险」 | 「已经滞库了」 |
| 计划 | 「2026 年 10 月月初版本，来源人工提报」 | 「已发布正式计划」 |

建议的标准格式：建议内容（做什么）+ 建议理由（为什么）+ 优先级（高/中/低）+ 建议责任角色 + 状态【待人工确认】。P1 不写责任人姓名。

## 四、业务判断边界

| 现象 | 不等于 | 原因 |
|---|---|---|
| 低于目标库存 | 当前订单缺货 | 目标是水位值，交付风险要看订单扣减后可供库存与缺货量 |
| 当前订单缺货 | 建议补货量 | 补货建议还要看库存差额并扣除调拨中 |
| 库存高 | 不需要补货 | 订单扣减后可供库存可能仍低于目标，备单中订单可能尚未占用 |
| 物理现库存高 | 可供订单的库存充足 | 需扣除备单中剩余未占用量后判断 |
| 货龄 60 天以上 | 大日期 | 分仓大日期阈值为 91 天及以上，61-90 天是重点消化区间 |
| 货龄 91 天及以上 | 已定责 | 大日期只说明需要处理，不定责 |
| 周转天数高 | 动销量最少 | 周转看覆盖周期，动销看实际数量，两者不能互相替代 |
| 动销偏慢 | 一定滞库 | 还需结合库存差额、货龄、计划与客户信号 |
| 客户库存低 | 分仓必须补货 | 客户信号是辅助输入，仍需结合分仓缺货量、库存差额与调拨中 |
| 基地有未来排产 | 分仓一定可按时到货 | 排产是计划供给，还需看基地库存、其他分仓需求、调拨规则与到货安排 |
| 人工计划已保存 | 已是有效计划 | 需覆盖该版本需要的 SKU 范围，否则标记人工计划不完整 |
| 保存下单量 | 已提交下单 | 提交后仍以专业系统返回状态为准 |
